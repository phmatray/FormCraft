## Integration style
- **Merge mode:** **squash** (recent subjects on a linear `dev` all read `… (#issue) (#PR)`).
  One documented exception: the #197 reconciliation PR (**#201**) must be merged with a **merge
  commit**, not squashed — a squash creates a new commit and leaves `v3.1.0` unreachable from `dev`,
  which would make release-please compute its first release over the whole project history.
  ⚠️ **Verify before trusting this line:** run
  `git merge-base --is-ancestor v3.1.0 origin/dev; echo $?` — `0` means #201 landed correctly.
  Everything else squashes.
- **PR title convention:** Conventional Commits prefix, **enforced by `pr-title-lint.yml`** since
  #197 (it used to be house convention with nothing checking it) —
  `<type>(<scope>): <subject> (#<issue>)`. Because the repo squash-merges, the PR title *becomes*
  the commit on `dev` that release-please parses to compute the next version: a non-conforming
  title yields no release. Scopes in use: `mudblazor`, `lov`, `deps`, `renovate`, `release`.
  Types in use: `feat`, `fix`, `chore`, `docs`, `ci`, `test`. Derive the type from the issue's type
  label (`type:bug` → `fix`, `type:feature` → `feat`); never pass the issue title through verbatim.
  Squash appends the PR number → the `dev` commit reads `<type>(<scope>): <subject> (#issue) (#PR)`.
- **Branch naming:** `feat/<issue>-<slug>` (this skill's default; the repo shows `ci/…`, `chore/…`
  prefixes too — the prefix is not enforced)

## Conflict hot-spots (merge-with-main resolutions)
| File | Why it collides | Resolution |
|------|-----------------|------------|
| `README.md` → `## 🎉 Unreleased` | every feature appends a release-note bullet here | **union** — keep both bullets |
| `README.md` (rest) + `docs/` | parallel features document themselves | **union** |
| `CHANGELOG.md` | **release-please** owns it — it is rewritten in the standing release PR | take the **release PR's** version; **never hand-edit, never hand-merge**. Nothing in the build generates it any more (git-cliff and `cliff.toml` were removed in #197) |
| `Directory.Build.props` / `Directory.Packages.props` | version pins and package bumps | package versions: take the **higher**; property edits: union |
| `FormCraft.sln`, `*.csproj` | both sides add files/projects | **union** the item groups |
| Test files | both sides append tests | **union** |
| `*.razor` / `*.razor.cs` renderers | two features touching the same render path | real semantic conflict — read both intents, don't pick a side blindly |
- **No `<Version>` element to bump:** versioning is **MinVer** from git tags (`MinVerTagPrefix=v`), so
  there is no version file to take-the-higher on. Don't invent one. Since #197 **release-please
  creates that tag**; `release-please-config.json` deliberately has **no `extra-files`** for the same
  reason (a written `<Version>` would be inert — MinVer's targets override it). Keep
  `include-component-in-tag: false`, or tags stop matching `MinVerTagPrefix=v` and packages pack as
  `0.0.0-alpha`.
- **Releasing:** merge the release PR release-please keeps open against `dev`. Tag, changelog,
  GitHub Release and both NuGet packages all follow from that one action. **Never tag by hand.**
- **Rule of thumb:** union additive files, regenerate derived files; same-logic-both-sides is a real
  semantic conflict — understand both intents or stop.

## Architecture grain / invariants (shape implementation plans to these)
- **`FormCraft` (core) is UI-framework-agnostic.** No MudBlazor type may leak into it. UI-specific
  code belongs in `FormCraft.ForMudBlazor`.
- **Two render paths exist and must agree.** Ordinary fields go through the *declarative* path
  (a `.razor` component per field type, via `IFieldRendererService`); fields inside
  `.WithItemForm(...)` go through the *imperative* path (`CollectionFieldComponent` building the tree
  with `RenderTreeBuilder`). `RenderPipelineParityTests` exists to keep them honest — presentation
  attributes have repeatedly drifted between them (see #146, #177, #184).
- **`RenderTreeBuilder` sequence numbers are a shared index space** between
  `AddCommonFieldAttributes` and its callers. Adding an attribute shifts every caller's starting
  offset; get it wrong and attributes silently overwrite each other.
- **Builders are fluent and immutable-after-`Build()`.** `Add*` adds, `With*` configures,
  `Enable*` toggles; no side effects in builder methods.
- **Validation is server-side only** — `Required()` adds a validator but not the HTML5 attribute;
  forms render `novalidate`.
- **Tests:** xUnit + Shouldly, Arrange-Act-Assert; MudBlazor component tests derive from
  `MudBlazorTestBase` (bUnit).
- `TreatWarningsAsErrors=true` **is** deliberate here — do not relax it to make a build pass.
